- G10, the skill: `skills/mirror/SKILL.md` gives an agent one fixed order (`setup --dry-run` shown to the person, the keys to make, `setup`, `key set` run by the person, the first copy announced and the person's go, `sync`, `status`, `restore --check`), names every step that is the person's with what to say, and says what never to do.

- G9, upgrades and uninstall: the forge always runs the Gitea its state names, so a new release of the skill never changes the forge by itself, and `setup` will not move it. `upgrade-forge` moves only to the version this release pins, never back: a backup first, the new binary checksum-checked, the forge stopped, migrated, started and checked; on any failure the old binary and the database as it was come back. `self-update` installs the latest release's `mirror.py` only when its checksum matches the one in the release notes, checks that it runs, and replaces the file whole in one rename, never while a sync runs. `uninstall` removes the service, the timer, the binary, the settings and every key, and leaves the folder of copies, which `uninstall --delete-copies` deletes only after the person types how many copies it holds.

- G8, this computer only: `status` tries the forge's port on every address of this computer's own network interfaces and reports a problem if it answers on any but 127.0.0.1. The skill writes no setting that opens the forge and runs no tunnel; `expose` says what opening it would mean and changes nothing. `setup`, the first-copy announcement and the README all say: the copy is as private as this computer.

- G7, restore: each fetch writes down the branches and tags GitHub showed. `restore --check` clones every copy from the forge with every other host shut off, checks each branch and tag against what GitHub last showed, checks the large files and runs `git fsck`, then removes its scratch folder. `restore --to <url> <owner/name>` puts one copy, every branch and tag and its large files, into a new, empty home the person names; it refuses a home that is not empty, and it never pushes to GitHub (it shows the person the two commands to do that themselves). `backup <folder>` stops the forge, takes Gitea's own dump plus the skill's state and settings (never a key), starts the forge again, and writes one file only the person can read. `setup --from <file>` on a new computer brings every copy back, with a new key for the mirror account; the GitHub keys are made again.

- G6, status: `status` prints one line per problem, then `copies: N on GitHub, N copied, M behind, U unreadable`. A copy is current only when its last good refresh is within twice the sync interval, nothing stopped it, and the forge itself holds exactly the branches and tags GitHub last showed; there is no pardon. It scans every repository config in the forge and the skill's own files for anything shaped like a key, and a scan that read nothing is a failure. It shows the forge's version, each key's expiry (14 days ahead is a problem), free disk, the last good sync and the next. Once a day it asks GitHub, with no key, for this skill's latest release, and says when that release pins a newer Gitea and whether it names it a security fix; it changes nothing. Every key and password the skill reads is kept out of everything it prints.

- G5, never lose a commit: before a branch or tag of a copy is rewritten, moved back or deleted to follow GitHub, its old commit is kept in the same copy as `kept/<date>/<name>` (a tag as `kept/<date>/tags/<name>`), and the sync says so. A kept ref is dropped after 90 days by default (a setting); with the default, one that is the only way to its commit stays. Every push into the copy is one atomic push with explicit deletes, and the copy's own refs are read back before each push, so a lost local cache is rebuilt with its kept refs. A push to GitHub cannot start: GitHub's push address in every cache is a dead one, and the only call to GitHub's API is a read.

- G4, stay current: `setup` also switches on a timer that runs `sync` every 15 minutes (a setting). It copies nothing before the person's go, and `status` reads the timer's next run, so a timer that is on with no next run is a problem. Every fetch and push has a time limit and one retry, and a slow repository is named while the others carry on. Only one sync runs at a time, and a lock whose sync is gone is taken over. Listing stops below a floor of GitHub's remaining allowance. A sync does not start below a floor of free disk. Large files go in first and then the branches and tags in one atomic push, and a copy in progress is marked until it is done. A sync fetches only the repositories whose `pushed_at` moved, and once a day it does a full pass.

- G3, find and copy: `sync` lists every repository of each owner page by page to the end, with that owner's key, and copies branches, tags and large files into a private copy each, known by GitHub's id: a rename follows, a reused name moves the old copy aside, a repository gone from GitHub keeps its copy. The key is only ever in the fetching process's environment. `config include|exclude` chooses; an include that matches nothing stops. `sync --announce` comes before the first copy. A copy that comes back not private is deleted at once and the sync stops. G2.5: a new key is one step, and the next sync proves it.

- G2.2, the keys: `key set <owner>` reads one owner's GitHub key from standard input (never a command line), checks that it reaches that owner's repositories, and keeps it in a file of its own that only the person can read. A refused key, or one that cannot see the owner, is not kept.

- G1, the forge: `setup` installs stock Gitea 28.4.0 (pinned, checksum checked) as the person's own service, on 127.0.0.1 only, with sign-up closed, Actions and Gitea's own mirrors off, and two accounts (the person's, and `mirror` that owns the copies). `setup --dry-run` changes nothing; a second `setup` changes nothing. Setup says when the copy will not come back by itself after a restart.
